# FoundryFabric fork of pgplex/pgparser

Branch `ff` is upstream `v0.2.0` plus the patches below. Tags are
`v0.2.0-ff.N`. The module path stays `github.com/pgplex/pgparser`, so a
consumer selects this fork with a `replace` directive and drops it once
upstream ships the fix.

| patch | file | pinned by |
|---|---|---|
| PARAM carries its `$N` number into the grammar's semantic value (every `ParamRef.Number` was 0) | `parser/parse.go` | `TestLexCarriesParamNumber` |
| Identifiers of 64+ bytes, quoted or not, are truncated to at most 63 bytes on a UTF-8 character boundary (pg_mbcliplen), as PostgreSQL 16's truncate_identifier does. `Parse(input, opts ...Option)` takes one option, `WithNoticeHandler(func(Notice))`, which reports each truncation in source order as `Notice{Code: "42622", Message: PostgreSQL's text}` (no position, as PostgreSQL sends none) | `parser/lexer.go`, `parser/parse.go` | `TestLexerTruncatesIdentifiers`, `TestParseNoticesInSourceOrder` |
| Unquoted identifiers have only ASCII `A`-`Z` lowercased, and keyword lookup folds ASCII case only, as PostgreSQL 16's downcase_identifier and ScanKeywordLookup do in a multibyte encoding (`Éa` stays `Éa`, `İx` stays `İx`; KELVIN SIGN + `ey` is an identifier, not `KEY`). `strings.ToLower` lowercased all Unicode and could change byte length, so truncation was computed on the wrong form | `parser/lexer.go`, `parser/keywords.go`, `cmd/pgsema-gen/main.go` | `TestParseDowncasesASCIIOnly`, `TestParseNonASCIIIsNeverAKeyword`, `TestParseTruncatesDowncasedForm` |
| `Parse` returns the scanner's errors, which it dropped: a malformed literal (`0x`, `0o8`, `1e`, `123abc`) parsed as a SELECT with no target, and `1_`, `1__0`, `0x1__0` were read as numbers. Numeric literals follow scan.l's `decinteger`/`hexinteger`/`numeric`/`real` rules and their fail and junk rules; `E''` and `U&''` escapes follow scan.l's `xeunicode`/`xeunicodefail`/`xeu` and parser.c's `str_udeescape`, surrogate pairs included. Every scanner error is a `*ParseError` with PostgreSQL 16's SQLSTATE (`42601`; `22025` for an incomplete `\u`), message (`... at or near "..."`), hint and position, and ends the token stream. `ParseError` gains `Code` and `Hint`, and its `Position` is now the 0-based offset of the token the error is at (PostgreSQL reports it 1-based) for grammar errors too: it was the lexer's offset after its lookahead | `parser/lexer.go`, `parser/parse.go` | `TestParseReportsLexerErrors`, `TestParseErrorPositionIsTheRefusedToken`, `TestParseLexerErrorPrecedesSyntaxError`, `TestParseAcceptsWellFormedLiterals` |
| Seven node kinds carry PostgreSQL's location: goyacc has no Bison `@N`, so `%union` gains `loc` (set from `Token.Loc` in `Lex`; a nonterminal inherits its first symbol's, as goyacc copies `$1` into `$$`), and `RangeVar`, `ColumnRef`, `ParamRef`, `A_Const`, `A_Expr`, `FuncCall` and `TypeCast` take `Location` from the symbol PostgreSQL 16's gram.y names with `@N` (`-1` where PostgreSQL passes `-1`). The helpers take a location as PostgreSQL's do (`makeIntConst`, `makeStringConst`, `makeBoolAConst`, `makeNullAConst`, `makeAExpr`, `makeStringConstCast`, `makeTypeCast`, `makeRangeVar`, `doNegate`, which puts a negated constant at its minus sign). Every other node kind keeps its old value (`-1`, or `0` where the grammar never set one): `A_ArrayExpr`, `BoolExpr`, `BooleanTest`, `CaseExpr`, `CaseWhen`, `CoalesceExpr`, `CollateClause`, `ColumnDef`, `CommonTableExpr`, `Constraint`, `DefElem`, `GroupingFunc`, `GroupingSet`, `MinMaxExpr`, `NamedArgExpr`, `NullTest`, `ResTarget`, `RowExpr`, `SQLValueFunction`, `SetToDefault`, `SortBy`, `SubLink`, `TypeName`, `WindowDef`, `XmlExpr` and the rest. `make check-parser` fails when goyacc (pinned to `v0.40.0`, the version that reproduces the committed tables) does not regenerate `parser/parser.go` and `parser/y.output` byte for byte | `parser/gram.y`, `parser/parse.go`, `parser/parser.go` (generated), `Makefile` | `TestLocationsArePostgreSQLs`, `make check-parser` |
| `LIMIT #,#` is refused as PostgreSQL 16's grammar refuses it: `42601` `LIMIT #,# syntax is not supported`, HINT `Use separate LIMIT and OFFSET clauses.`, at the LIMIT keyword. It was parsed as OFFSET and LIMIT. A grammar action raises an error through `grammarError` (the first one stands) and ends the parse with `return 1`, as PostgreSQL's `ereport` does | `parser/gram.y`, `parser/parser.go` (generated) | `TestParseRefusesLimitComma` |
